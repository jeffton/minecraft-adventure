# Roycraft: observed play and improvement

Run this workflow when the Minecraft evaluation job fires. Read the canonical `PLAYER_OBJECTIVE` in `player/mission.mjs`; evaluate progression toward that selected user objective in the existing world, not more controller code.

## Authority and state

- Read the latest user instructions and current service status first. A user stop or changed mission takes precedence. If `minecraft-player.service` is inactive, do not start it: report that evaluation has stopped and delete this evaluation cron job. Never start the retired four bots. Do not restart Roy against a user stop.
- Preserve world, inventory, notes, full event/action/controller history and credentials. No resets, deletions, third-party messages, purchases or Batty changes.
- State: `/var/lib/minecraft-player/player-20261101/`. Current observations: `/var/lib/minecraft-adventure/observations/state.json`. Runtime code: `/opt/minecraft-adventure/player/`. Source: `/root/github/minecraft-adventure`. Public view: https://minecraft.roybot.se/.
- Read `/var/lib/minecraft-player/evaluation.json` if present. Record evaluation time, player session, source commit, active mission/version, observations, diagnosis, changes and evidence timestamps there after each evaluation. It is evaluation bookkeeping, not proof of gameplay.

## Evaluate actual outcomes

1. Verify Node 26 and player health (`http://127.0.0.1:8766/healthz`). Inspect actual observation, `progress.json`, controller state, recent events and action records since the last evaluation. Filter large files locally; do not paste whole histories or credential files into context. Use real POV/viewer if terrain or building quality matters.
2. Measure the chosen base site and actual cover, acquired/retained wool and wood, crafted/placed usable bed and actual sleep, and construction growth from cave shelter into a house. Verify blocks and inventory rather than treating returned claims as success. For bed/spawn claims, record actual successful sleep RPC/server acknowledgement and bed dimension/location, sleep-to-wake/time change, and any later ordinary respawn or spawn-reset evidence. Bed placement, narrated success and the world/compass `spawn_position` do not establish personal bed spawn. Evaluate the user's preference for sleeping overnight and the prerequisite for a night trip: actual verified Overworld bed use plus nonessential stock secured at home, with only necessary supplies carried. Missing bed/chest should drive useful preparation, not another unsecured expedition; this remains model planning, not mechanical enforcement. Check actual home-chest crafting and placement, container-confirmed deposits and withdrawals, and the stock secured at home versus carried supplies. Assess whether storage happens on natural returns or when risk warrants it, while needed equipment, food and immediate materials remain available; do not reward a separate home trip for every acquired item. Track retained resources, food/health, deaths, lost equipment or base damage, and navigation: net vs gross travel, new locations and repeated destinations. Separate historical totals from this interval; relocation, scans and action completion alone are not progress. Let the model choose site, work order, materials and design. Clock, sunrise/sunset and thunder are planning facts, not grounds for a host-enforced curfew or prescribed shelter geometry.
3. Evaluate the user's home-lighting priority using actual placed light-source blocks and received blockLight at potential mob feet positions inside and around the home, entrances and approaches. Separate acquired torches/charcoal, crafted output, placed lights and measured coverage. Raw skyLight is not a night-adjusted value; daylight or a bright renderer does not prove permanent block-light coverage. Positive block light prevents ordinary natural spawning for most Java Overworld monsters, not existing mobs entering or all special spawns. Report observed dark gaps, mobs and resource blockers; do not invent a safety percentage, fixed spacing/quota or complete spawn-proofing from sparse samples. Recheck after server light updates and as the home expands.
4. Track the continuing house-and-dragon objective alongside the immediate base: permanent house quality and retained stock, useful tools/armor and food, observed Nether entry and return, blaze rods/pearls/Eyes, stronghold and End-portal discovery/activation, and actual dragon combat/defeat. These are planning milestones, not a fixed host-enforced sequence; do not count names in notes as completion. Verify dimension transitions and report real tool/protocol blockers without assuming portal or End compatibility. Roy has no web-search tool; the high-level roadmap lives in `mission.mjs`.
5. Inspect the active mission, its expected outcome, actual result and remembered lessons. Check that the next strategy incorporates failures rather than replaying the same movement. Inspect model/tool errors, latency and token usage; do not repeatedly trigger expensive full-history analyses. The strategist must choose concrete achievable missions, with local skills and survival reflexes handling execution.
6. Observe enough new actual decisions/outcomes to distinguish a transient obstacle from a loop. Do not sleep or busy-poll subagents; use bounded fresh evidence collection or schedule an appropriate next evaluation. Never claim progression without observed evidence.

## Improve only a demonstrated weakness

- If play progresses intelligently, leave code alone. Report concrete progress even when no edit is needed.
- Diagnose the cause before an edit. Prefer improving the mission, useful memory, perception/outcome projection or a concrete RPC defect over a new universal decision tree or another anti-loop patch.
- Pull before coding, preserve unrelated dirty files (legacy `bots/` and `planner/` may contain pre-existing work), coordinate other workers, and implement only targeted Minecraft changes. Test/build using the relevant package scripts; obtain independent Sol-medium review before completion, address findings, commit and push owned changes. Deploy player changes through `bash player/deploy.sh`; static diary changes use `bash diary/publish-ui.sh`. Never deploy Batty or restart Paper to fix planner behavior.
- After any deployment or strategic change, verify actual subsequent gameplay, fresh source/version, health and real outcomes. If the provider or game is blocked, record/report the concrete blocker, not invented success or repeated model calls.
- Keep exactly one evaluation job. Its initial checks are roughly 10 and 30 minutes after activation, then every two hours. Preserve that cadence while Roy runs; stop/delete it when Roy is explicitly stopped. The cron prompt references this file instead of duplicating the workflow.

Deliver a short Danish result with observed progress, any demonstrated weakness/fix and important blocker. Do not repeat unchanged status verbatim; explain the current evaluation's actual evidence. Never include secrets.
